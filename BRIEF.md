Платформа для командной разработки с AI-агентами. Проект объединяет сотрудников, репозитории и подключения к рабочим сервисам. Встроенный помощник помогает разобраться в проекте и передать работу коллеге вместе с нужными источниками.

## Первая версия

- Администратор создаёт проект, подключает один или несколько репозиториев GitHub и выдаёт сотрудникам доступ. В первой версии помощник читает документацию из этих репозиториев.
- Встроенный помощник отвечает на вопросы по доступным источникам и ссылается на них. По поручению сотрудника он готовит черновик задачи. Сотрудник проверяет черновик и назначает задачу коллеге на платформе.
- Рабочий агент через MCP получает задачи, назначенные сотруднику, и доступные сотруднику материалы проекта. Платформа проверяет права сотрудника при каждом запросе.

## Что показать

1. Сотрудник спрашивает, как устроен возврат заказа. Помощник находит описание процесса и нужный репозиторий, объясняет, с чего начать, и даёт ссылки.
2. Сотрудник просит подготовить задачу по уведомлениям о возвратах. Он проверяет черновик и назначает задачу коллеге. Коллега открывает задачу и источники через своего рабочего агента. После отзыва доступа следующий запрос того же агента получает отказ.

## Учебный проект

Команда строит внутреннюю платформу, через которую сотрудники поручают работу своим агентам и обращаются к агентам коллег. Встроенный помощник служит точкой входа. Сервер знает, кто дал поручение, какому агенту его передали, какие действия ему разрешены и кому вернуть результат.

### Вариант демонстрации с двумя сотрудниками

Для первого практикума можно объединить четыре модуля: каталог агентов, передачу поручения, проверку прав и мониторинг.

1. Сотрудник поддержки открывает обращение о двух одинаковых письмах и просит помощника выяснить причину. Помощник находит агента дежурного разработчика. Агент поддержки передаёт ему номер возврата и вопрос о повторной доставке.
2. Дежурный открывает поручение под своей учётной записью, видит запрос и указывает период проверки. Его агент читает журнал доставки и находит две попытки отправки.
3. Сотрудник поддержки возвращается в исходный разговор и видит разрешённую сводку с числом и временем попыток. Подробный журнал доступен дежурному.
4. Преподаватель открывает историю поручения и показывает, кто начал проверку, какой агент прочитал журнал, где работа ждала человека и какие данные сервер передал поддержке.

## Возможные серверные модули

Это варианты развития после первой версии. Каждый модуль можно показать на одном поручении с двумя сотрудниками.

| Возможность | Что делает сервер | Что увидят студенты |
|---|---|---|
| Каталог агентов сотрудников | Хранит владельца, доступные команде функции и способ связи с агентом. Предлагает исполнителей с учётом проекта и прав инициатора. | Помощник находит агента дежурного по запросу «проверь повторы доставки». При смене дежурства следующее поручение получает другой агент. |
| Поручения между агентами | Создаёт дочернее поручение с адресатом, разрешёнными входными данными и ссылкой на исходную задачу. Сохраняет вопросы, ответы и результат. | Агент дежурного запрашивает период проверки. Агент поддержки уточняет период и получает ответ в исходной сессии, даже если сотрудник закрыл чат. |
| Общая сессия с помощником | Хранит участников, события и состояние работы. Доставляет уточнения и команды остановки активному исполнителю. | Коллега открывает поручение, видит, кто сейчас работает, и сужает запрос до одного магазина. Исполнитель подтверждает, что принял уточнение. |
| Доступ от имени сотрудника | Проверяет сотрудника, агента, поручение и операцию при обращении к сервису. Отдельно проверяет, какие результаты разрешено вернуть инициатору. | Агент разработчика читает закрытый журнал, поддержка получает число повторов. После отзыва доступа следующий вызов из той же сессии получает отказ. |
| Входящие согласования | Сохраняет предложенное действие и его параметры, назначает согласующего, принимает решение один раз и будит ожидающий запуск. | Дежурный правит текст уведомления. Платформа показывает окончательный текст на утверждение. Два нажатия на кнопку приводят к одной отправке. |
| Среда выполнения и очередь | Выдаёт исполнителю отдельное окружение, ограничивает время работы и фиксирует завершённые шаги. После сбоя передаёт работу свободному исполнителю. | Первый исполнитель отключается во время ожидания. Второй продолжает с сохранённого шага, и участники получают один итоговый ответ. |
| Шлюз к рабочим инструментам (MCP Gateway) | Подключает сервисы компании, выдаёт доступные операции и записывает вызовы с указанием поручения. | Оба агента подключаются к одному адресу. Агент поддержки видит обращения, агент дежурного запрашивает технические события. |
| Шлюз к моделям (LLM Gateway) | Направляет запросы к выбранной модели, учитывает расход помощника и дочерних агентов по одному поручению и применяет бюджет проекта. | Владелец видит стоимость всего расследования. Если остатка бюджета недостаточно, новый вызов ждёт решения владельца. |
| Мониторинг всей цепочки | Связывает события помощника, агентов и шлюзов с одним поручением. Отличает время в очереди, работу модели, ожидание сервиса и ожидание человека. | У руководителя три незавершённых поручения. Он видит, за какое отвечает дежурный, где недоступен сервис и где агенту нужен ответ коллеги. |
| Запуски по событиям | Принимает события рабочих систем, проверяет правила команды и распознаёт повторную доставку. Сохраняет связь между событием и поручением. | Тестовый монитор дважды присылает один сигнал о дубликатах. Появляется одно расследование с назначенным дежурным и ссылкой на сигнал. |

## На какие решения можно посмотреть

- Для каталога подойдёт пример Glean. Сотрудник может найти и запустить доступного ему агента. [Каталог агентов Glean](https://docs.glean.com/agents/concepts/agent-library)
- Для обмена поручениями можно взять идеи из протокола A2A. Удалённый агент публикует карточку с возможностями, принимает задачу и возвращает результат по её идентификатору. [Основные понятия A2A](https://a2a-protocol.org/latest/topics/key-concepts/)
- Для общения во время работы интересен Linear. Агент запрашивает уточнение, сотрудник отвечает, а Linear сохраняет оба события в одной сессии. [Сессии агентов Linear](https://linear.app/developers/agent-interaction)
- Для очереди исполнителей есть пример Paperclip. Если за поручением одновременно пришли два агента, сервер закрепляет его за одним. Этот агент может повторить запрос после потери ответа. [Получение задачи в Paperclip](https://docs.paperclip.ing/guides/projects-workflow/routines/#5-checkout)
- Для шлюза полезен Amazon Bedrock AgentCore Gateway. Разработчик может подключить отдельные обработчики для проверки запроса к инструменту и обработки ответа перед передачей агенту. [Обработчики AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors.html)
- Для мониторинга подходит пример Langfuse. Несколько вызовов можно объединить в одну сессию, восстановить последовательность и открыть детали отдельного шага. [Сессии в Langfuse](https://langfuse.com/docs/observability/features/sessions)

Дополнительные сценарии для занятий собраны в [обзоре серверных функций](docs/research/team-agent-platforms.md).
