# Прототип spec48: платформа как OAuth-сервер для MCP

❗ Это одноразовый прототип. Его код не идёт в продукт, ветку не мержим.

Прототип отвечает на вопрос, сможет ли OpenCode v2.2.7 подключиться к MCP платформы, если OAuth-токены выдаёт сама платформа, а сотрудник входит через Keycloak. Всё состояние хранится в памяти процесса и пропадает при перезапуске.

```
prototypes/spec48-mcp-oauth/
  server.mjs                  платформа: OAuth-сервер, согласие, /mcp, страница подключений
  selftest.mjs                самопроверка всего сценария через MCP SDK
  compose.yaml                Keycloak 26.8.2 на 127.0.0.1:18480
  keycloak/spec48-realm.json  realm spec48, клиент platform, пользователи anna и boris
```

## Запуск

Нужны Node 24 и Docker. Команды выполняются из этой папки:

```sh
npm install
docker compose -p proto-spec48-mcp up -d   # Keycloak стартует около минуты
ACCESS_TTL_SEC=60 npm start                # платформа на http://127.0.0.1:18481
npm run selftest                           # отдельный экземпляр на 18482, срок токена 5 с
docker compose -p proto-spec48-mcp down    # остановить Keycloak
```

Страница подключений: <http://127.0.0.1:18481/connections>. Там видны все подключения, кнопки «Отозвать» и полный дамп состояния. Страница обновляется каждые 5 секунд.

Настройки через переменные окружения:

| Переменная | По умолчанию | Что задаёт |
| --- | --- | --- |
| `ACCESS_TTL_SEC` | 900 | срок access token платформы |
| `IDLE_TTL_SEC` | 2592000 (30 дней) | срок неактивности подключения; подключение живо, пока `now < lastUsed + N` |
| `KC_TIMEOUT_MS` | 3000 | сколько ждать Keycloak при refresh |
| `STATIC_CLIENT_ID` | `spec48-opencode` | заранее зарегистрированный public client |

## Как устроен сервер

1. OpenCode обращается к `/mcp` без токена и получает `401` с `WWW-Authenticate: Bearer resource_metadata=".../.well-known/oauth-protected-resource/mcp"`.
2. Metadata ресурса (RFC 9728) называет платформу сервером авторизации. Metadata сервера (RFC 8414) объявляет `S256`, `/register` и `client_id_metadata_document_supported: true`.
3. `/authorize` принимает клиента одним из трёх способов и пишет способ в журнал и в подключение:
   - `static`: заранее зарегистрированный `spec48-opencode`;
   - `cimd`: `client_id` равен HTTPS URL документа клиента, платформа скачивает и проверяет документ;
   - `dcr`: клиент сначала регистрируется через `/register`.
4. Платформа принимает только loopback redirect по http (127.0.0.1, [::1], localhost) и сравнивает его без порта, как требует RFC 8252.
5. Платформа отправляет сотрудника на вход в Keycloak: Authorization Code + PKCE, confidential client на backend, scope `openid email profile offline_access`. SSO-cookie Keycloak служит веб-сессией сотрудника, поэтому при повторном подключении пароль не спрашивается.
6. Страница согласия спрашивает «Подключить <клиент> от имени <email>?». После «Подключить» клиент получает одноразовый код на 60 секунд, привязанный к PKCE, redirect_uri, клиенту и resource.
7. `/token` создаёт подключение и хранит в нём refresh token Keycloak. Access и refresh token платформы случайные; платформа хранит только их SHA-256. Refresh token меняется при каждом обновлении.
8. На каждом запросе к `/mcp` платформа проверяет токен, его срок, состояние подключения и неактивность. Поэтому отзыв действует на следующий же запрос.
9. При каждом refresh платформа сначала обновляет токен в Keycloak:
   - если Keycloak отказал, платформа отклоняет refresh с `invalid_grant`, и подключение переходит в `provider_refused`;
   - если Keycloak не ответил, платформа отвечает `503 temporarily_unavailable`, а подключение остаётся активным.
10. MCP работает по Streamable HTTP через `legacyStatelessFallback` из `@modelcontextprotocol/server` 2.4.0, редакция `2025-11-25`. Инструменты `list_projects` и `get_project_context` только читают выдуманные проекты своего сотрудника.

## Чек-лист для владельца: OpenCode v2.2.7, около 30 минут

Прототип не трогает твой глобальный конфиг OpenCode. Конфиг ниже кладётся в отдельную пустую папку, и OpenCode запускается из неё.

1. Подними стенд: `npm install`, `docker compose -p proto-spec48-mcp up -d`, затем `ACCESS_TTL_SEC=60 npm start`. Открой <http://127.0.0.1:18481/connections>.
2. Поставь OpenCode ровно этой версии и запиши вывод версии:

   ```sh
   curl -fsSL https://opencode.ai/v2/install | bash -s -- --version 2.2.7
   # или: npm install -g @opencode/cli@2.2.7
   opencode --version
   ```

3. Создай папку, например `/tmp/spec48-opencode`, и положи в неё `opencode.jsonc`. Два имени с одним URL дают OpenCode два отдельных набора credentials, то есть два подключения на платформе:

   ```jsonc
   {
     "$schema": "https://opencode.ai/config.json",
     "mcp": {
       "servers": {
         // без oauth.client_id OpenCode выберет CIMD: платформа его объявляет
         "platform-cimd": {
           "type": "remote",
           "url": "http://127.0.0.1:18481/mcp",
           "protocol": "legacy"
         },
         // заранее зарегистрированный public client
         "platform-static": {
           "type": "remote",
           "url": "http://127.0.0.1:18481/mcp",
           "protocol": "legacy",
           "oauth": { "client_id": "spec48-opencode" }
         }
       }
     }
   }
   ```

   `"protocol": "legacy"` в OpenCode v2.2.7 открывает соединение через `initialize` и говорит редакциями до `2025-11-25`. Это значение по умолчанию, в конфиге оно записано явно. Значение `auto` сначала пробует `2026-07-28`, а `"2026-07-28"` требует только новую редакцию. Источник: схема `Mcp.Protocol` в `packages/schema/src/mcp.ts` и функция `negotiation` в `packages/core/src/mcp/client.ts` на commit `fedc6f208aa2bd54c1019227214568083f6380ad`.
4. Запусти `opencode` в этой папке, открой `/mcps` и подключи `platform-cimd`. В браузере войди как `anna` / `anna-pass` и нажми «Подключить». На странице подключений проверь способ регистрации `cimd`.
5. Попроси агента: «Покажи мои проекты через list_projects и контекст проекта alpha». Ожидается Альфа и Бета; для `gamma` ответ «Нет доступа».
6. Закрой OpenCode, запусти снова и начни новую беседу. Повтори просьбу: агент должен прочитать проекты без нового согласия.
7. Подключи `platform-static` тем же способом. На странице должно стать два активных подключения `anna`, способы `cimd` и `static`.
8. Нажми «Отозвать» у `platform-static`. Сразу попроси агента прочитать проекты через `platform-static`: ожидается отказ. Через `platform-cimd` чтение продолжает работать.
9. Отключи `anna` в Keycloak: консоль <http://127.0.0.1:18480/admin>, `admin` / `admin`, realm `spec48`, Users, `anna`, выключи Enabled, Save. Подожди до 60 секунд, то есть один срок токена, и попроси агента прочитать проекты. Ожидается отказ, а подключение на странице переходит в «отказ провайдера».
10. Включи `anna` обратно. Старое подключение остаётся в отказе; новое подключение после согласия работает.

Что записать:

- вывод `opencode --version` и ОС;
- какой способ регистрации показала страница подключений для каждого имени сервера;
- что OpenCode показал при отказе после отзыва и после отключения `anna`: `needs_auth`, ошибку или повторный вход;
- скриншоты страницы согласия и страницы подключений. Дамп состояния на странице показывает только первые символы хешей токенов, но перед публикацией всё равно проверь, что в кадре нет токенов и кодов.

Третий способ, DCR, проверяется так. Добавь сервер `platform-dcr` с тем же URL и `"oauth": { "callback_port": 19876, "redirect_uri": "http://127.0.0.1:19876/callback" }`. Со своим `redirect_uri` OpenCode не использует CIMD и регистрируется через `/register`.

## Что показала самопроверка

`npm run selftest` прошёл 32 проверки из 32 на `@modelcontextprotocol/client` 2.4.0. Этот же пакет использует OpenCode v2.2.7, но OpenCode применяет к нему небольшой патч. Форму входа Keycloak скрипт заполняет так же, как браузер; direct grant нигде не используется.

- Все три способа регистрации прошли: `static`, `cimd` и `dcr`. Для CIMD скрипт взял настоящий документ OpenCode `https://opencode.ai/oauth/opencode/client.json`, поэтому самопроверке нужен интернет. SDK принимает `clientMetadataUrl` только с HTTPS, а документ OpenCode перечисляет redirect без порта.
- Клиент и сервер согласовали `2025-11-25` через `initialize`.
- Отозванное подключение получает `401` на неистёкший access token, refresh отклоняется, другие подключения того же сотрудника работают.
- Keycloak на refresh отключённого пользователя отвечает `400 {"error":"invalid_grant","error_description":"User disabled"}`, удалённого `400 {"error":"invalid_grant","error_description":"Offline user session not found"}`. Вход отключённого пользователя Keycloak показывает на форме: «Account is disabled, contact your administrator.»
- Если Keycloak не отвечает (контейнер на паузе), платформа через 3,1 секунды отвечает `503 temporarily_unavailable`. Подключение остаётся активным, после возврата Keycloak refresh снова проходит.
- ❗ Если пользователя отключили и включили обратно до ближайшего refresh, подключение продолжает работать. Keycloak не удаляет offline-сессию при отключении, а платформа узнаёт об отключении только в момент refresh.

## Что прототип не доказывает

- Это не приёмка P-H02. Приёмку проводит владелец на согласованном стенде по спецификации.
- Это не безопасность для продакшена. Нет защиты от CSRF на согласии, нет входа на страницу подключений, нет TLS, нет хранилища, нет rate limit, тексты ошибок не согласованы.
- Права сотрудника выдуманы: проекты привязаны к email, а не к `iss` + `sub` и участиям.
- Деактивацию сотрудника в самой платформе прототип не моделирует; проверяется только отказ Keycloak.
- Прототип не проверял MCP `2026-07-28`.
