# Персональное MCP-подключение сотрудника

Дата проверки: 12 ноября 2026 года. Вопрос: [«Исследовать персональное MCP-подключение выбранного клиента»](https://github.com/KirillSachkov/ai-first-platform/issues/55). Карта: [«Подготовить решение для подключения сотрудника и агента к проекту»](https://github.com/KirillSachkov/ai-first-platform/issues/51).

## Вывод и границы свидетельств

Предлагаю проверить OpenCode **v2.2.7** через **Streamable HTTP и OAuth Authorization Code с PKCE**. Источники подтверждают браузерную авторизацию, сохранение учётных данных, обновление токенов и отдельные логические подключения к одному URL. Они дают основание для проверки кандидата, но ещё не подтверждают P05–P08 принятой [спецификации подключения](https://github.com/KirillSachkov/ai-first-platform/issues/48). В частности, независимый отзыв и актуальные права сотрудника должна обеспечить платформа.

Исследование ограничено документацией и исходниками. Клиент не установлен и не запущен, конфигурация пользователя, учётные записи и сервисы не изменены. Совместимость нашей будущей реализации с корпоративным OIDC остаётся непроверенной. Существенного документального пробела, который требовал бы другого клиента, пока нет; альтернативы не исследовались. Выбор OpenCode остаётся предложением владельцу.

Версия привязана к [релизу v2.2.7 от 10 ноября 2026 года](https://github.com/anomalyco/opencode/releases/tag/v2.2.7) и commit `fedc6f208aa2bd54c1019227214568083f6380ad`. В этом релизе исправлены конкурентное обновление rotating refresh tokens и потеря входа при временной ошибке token endpoint. Эти исправления прямо относятся к сохранённому подключению при нескольких процессах и проектах.

## Что подтверждает конкретный клиент

| Требование | Свидетельство OpenCode v2.2.7 | Что ещё проверить |
| --- | --- | --- |
| Персональное подтверждение | OAuth открывает браузер и принимает callback с проверкой `state`; код обменивается на токены | Платформа показывает сотрудника и запрашиваемое подключение; чужая личность не выдаёт разрешение за него |
| Новая сессия без повторного согласия | OAuth-данные записываются в общее хранилище credentials и читаются при подключении | Перезапуск процесса, новая беседа, истёкший access token и работающий refresh |
| Несколько подключений | Логическая идентичность вычисляется из имени сервера и URL; разные имена дают разные credentials | Два устройства создают два серверных подключения; отзыв одного сохраняет другое |
| Получение контекста | Клиент подключает tools и читает MCP resources | Фактическая выдача метаданных и указателей в пределах участия |
| Отказ после отзыва | Клиент передаёт OAuth-провайдер транспорту и обрабатывает ошибку авторизации | Сервер отклоняет новый запрос со старым токеном до его истечения |

Это результаты чтения [OAuth-адаптера](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/core/src/mcp/oauth.ts), [регистрации подключений](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/core/src/mcp/index.ts), [хранилища credentials](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/core/src/credential.ts) и [транспортного клиента](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/core/src/mcp/client.ts). Хранилище переживает отдельную беседу; срок доступности зависит также от политики сервера авторизации. Наличие refresh token не гарантируется клиентом.

Нельзя считать имя сервера, ID беседы OpenCode или транспортное соединение идентификатором персонального подключения платформы. Они имеют другой жизненный цикл. Платформа должна связать каждую выдачу полномочий с сотрудником и независимо отзываемым подключением. Повторное использование одного OAuth `client_id` несколькими установками само по себе этой связи не создаёт.

## Версия MCP и регистрация клиента

На дату проверки официальный адрес `latest` ведёт к [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization). У OpenCode v2.2.7 по умолчанию остаётся `protocol: "legacy"`, то есть handshake `initialize` для редакций до 2025-11-25. Значение `auto` сначала проверяет новый протокол и допускает переход к старому; `2026-07-28` требует именно новую редакцию. Это описывает [документация клиента](https://opencode.ai/docs/mcp-servers/#protocol-version), а исходник `client.ts` подтверждает настройку negotiation.

Для первой проверки предлагаю явно закрепить **`protocol: "2026-07-28"`** и соответствующий сервер. Если выбранный серверный SDK поддерживает только старую редакцию, сочетание нужно назвать отдельно и заново сопоставить с её требованиями. Автоматический fallback скрывал бы проверяемую версию. Новая [редакция транспорта](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) использует метаданные каждого запроса и отличается от прежних сессий с `initialize`. Долгоживущее подключение из предметной модели сохраняет смысл при обоих вариантах.

| Область | MCP 2026-07-28 | OpenCode v2.2.7 |
| --- | --- | --- |
| Обнаружение авторизации | Protected Resource Metadata указывает authorization server; клиент читает OAuth или OIDC metadata | OAuth-адаптер вызывает discovery SDK, учитывает challenge `401` |
| Идентификация клиента | Предварительная регистрация, затем CIMD, затем доступный DCR | Такой же порядок; CIMD требует поддержки public client и отсутствия собственного `redirect_uri` |
| Браузерный callback | Требования OAuth, PKCE и проверки issuer | Loopback callback, `state`, передача `iss` в SDK; полную совместимость подтвердит запуск |
| Сохранение доступа | Refresh зависит от authorization server | Клиент сохраняет access/refresh tokens, issuer и сведения регистрации |

[Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery) требует `authorization_servers` в metadata защищённого ресурса. Клиент ищет их через `WWW-Authenticate: Bearer resource_metadata=...` или well-known URL, затем проверяет совпадение `issuer` в metadata сервера авторизации. Публикации только OIDC discovery недостаточно для всей цепочки MCP.

[CIMD](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration) позволяет использовать HTTPS URL документа клиента как `client_id`. DCR, автоматическая регистрация через endpoint, в этой редакции deprecated и оставлен для совместимости. OpenCode также принимает заранее зарегистрированный public client. Встроенный секрет для локального CLI не требуется. Для CIMD авторизатор должен принять опубликованный документ OpenCode и loopback redirect с переменным портом. При DCR с OIDC отдельно проверяются `application_type: "native"` и допустимые redirect URI. Заявление MCP о поддержке механизма ещё не доказывает поддержку конкретным провайдером.

## Где заканчивается корпоративный вход

[OIDC Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html) описывает обнаружение провайдера и подтверждение личности. Из успешного корпоративного входа в веб-интерфейс не следует готовность выдавать MCP access tokens. В MCP есть три роли: клиент OpenCode, защищённый ресурс платформы и authorization server. Последний проводит OAuth-процесс и выпускает токены для этого ресурса.

Совмещение OIDC-провайдера и MCP authorization server возможно, если конкретный продукт и версия поддержат нужные metadata, public clients, PKCE, регистрацию, `resource`/audience, refresh и согласие пользователя. Другой вариант состоит в том, что платформа организует MCP OAuth и использует корпоративный OIDC для входа сотрудника. Это инженерные варианты, а не принятый выбор провайдера или поручение написать собственный authorization server.

На границе нужно проверить получателя токена, issuer, PKCE и callback. ID token от веб-входа нельзя автоматически использовать как MCP access token. Протокол требует токен для целевого ресурса, bearer-авторизацию каждого HTTP-запроса и отказ при недействительном токене. Это [требования MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#access-token-usage), а их выполнение нашим сервером пока не доказано.

## Отзыв и чтение принадлежат платформе

По принятой спецификации Edge проверяет подключение, активность владельца и актуальное разрешение через «Доступ». «Подключения агентов» владеют действительностью подключения. Проверка подписи JWT и `exp` покрывает только часть задачи. После подтверждённого отзыва платформа должна обнаружить новое состояние на следующем запросе, даже если старый access token ещё действителен по времени.

Из этого следует инженерное требование к будущей реализации: способ проверки и кеширования не должен оставлять окно выдачи после подтверждения отзыва. Возможны серверная проверка состояния или другой механизм с такой же гарантией. Конкретное хранение ещё не выбрано. Отзыв refresh token отдельно недостаточен, поскольку уже выданный access token может продолжать работать.

Отзыв проекта сохраняет другие участия. Отзыв подключения сохраняет другие подключения сотрудника. Деактивация закрывает новые выдачи всех подключений; восстановление не оживляет старые. Запрос, авторизованный до отзыва, может завершиться. Ранее скачанные данные остаются локально. Это критерии P07–P08, а не свойства OpenCode.

MCP должен публиковать только операции чтения разрешённого контекста. [Аннотации tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool) описывают поведение и не заменяют серверный запрет записи. Скрытие административной команды в интерфейсе клиента тоже не устанавливает границу доступа. Конкретный набор tools или resources ещё предстоит определить без изменения состава контекста P06.

## План проверки настоящим клиентом

Проверку P-H02 проводит владелец или назначенный сотрудник после отдельного разрешения эксперимента и появления тестового сервера. До этого достаточно завершить документальное исследование.

1. Зафиксировать ОС, вывод версии OpenCode, версии SDK и провайдера, MCP-редакцию, transport, способ регистрации и тестовый URL. Убрать токены и коды из протокольного свидетельства.
2. Лично пройти корпоративный вход и подтвердить подключение. Проверить отмену согласия, чужую личность и несовпадающий callback. Ожидать отсутствие подключения без нужного подтверждения.
3. Прочитать контекст двух разрешённых проектов и проверить отказ для чужого. Проверить, что MCP не предлагает административные операции и не выполняет запись прямым запросом.
4. Завершить процесс, начать новую беседу и повторить чтение без нового согласия. Дождаться контролируемого истечения access token и проверить refresh без повторного входа.
5. Создать второе подключение на другом устройстве. Отозвать первое и отправить новый запрос его ещё не истёкшим токеном. Ожидать отказ; второе подключение должно продолжить чтение.
6. Удалить одно участие, деактивировать и восстановить сотрудника. Проверить частичный доступ, общий отказ и отсутствие автоматического восстановления старых подключений. Отдельный контролируемый запрос проверяет границу авторизации до отзыва.

Неизвестны совместимость выбранного authorization server с CIMD или предварительной регистрацией, выдача refresh tokens, полный набор проверок issuer в используемом SDK и поведение клиента после серверного отказа. Документация и исходники не заменяют эти наблюдения. Перед экспериментом владельцу нужно принять кандидат и сочетание версий, выбрать среду и назначить человека для личного согласия. Изменения поведения или объёма возвращаются владельцу; исследование их не принимает.
