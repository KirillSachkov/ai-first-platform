# MCP в командах и роль платформенного помощника

Согласованный объём первой версии и сценарии демо описаны в [брифе проекта](../../BRIEF.md). Здесь собраны примеры и варианты, которые рассматривали перед его утверждением.

Для первой версии я бы поручил платформенному помощнику готовить задачу для рабочего агента. Он связывает запрос сотрудника с проектом, собирает доступные источники и предлагает карточку. Сотрудник подтверждает её, а рабочий агент забирает через MCP. Если нужен меньший срез, можно начать с помощника подключения.

## Три задачи для встроенного помощника

1. **Помощник подключения.** Сотрудник говорит, какой сервис хочет взять в работу. Помощник находит репозиторий, инструкцию и владельца. Затем помогает подключить рабочий агент и показывает результат настоящего запроса из этого клиента. Если запрос отклонён, сотрудник видит, какой шаг зависит от него, а какой от владельца проекта.
2. **Помощник подготовки задачи.** Сотрудник вводит короткое поручение или прикладывает запись прошлой сессии. Помощник связывает его с проектом, находит репозиторий и инструкцию, собирает цель, ограничения и следующий шаг в карточку. Сотрудник подтверждает карточку, рабочий агент получает её через MCP. Историю сессий можно добавить позже как ещё один источник.
3. **Помощник приёмки.** Человек открывает результат работы агента. Помощник сверяет поручение, PR и доступные проверки и показывает, какие критерии подтверждены и где ещё нужен ответ. Этот вариант имеет смысл, когда платформа видит результаты работы и проверок.

## Предлагаемый срез первой версии

Три функции для демо. Проект хранит ссылки на репозиторий и инструкции и ограничивает доступ к ним. Встроенный помощник готовит карточку работы из запроса и доступного проектного контекста. Рабочий агент читает согласованную карточку и её источники через MCP.

1. **Подготовка и передача задачи.** Сотрудник пишет «Подготовь задачу по повторной отправке уведомлений». Помощник находит репозиторий и инструкцию, собирает цель и отмечает открытые вопросы. Сотрудник подтверждает карточку. Его рабочий агент получает эту же карточку через MCP.
2. **Доступ отозван.** Администратор отзывает доступ к проекту. Тот же уже подключённый рабочий агент повторяет запрос и больше не получает карточку и контекст проекта.
