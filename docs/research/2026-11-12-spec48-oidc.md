# Корпоративный OIDC для подключения сотрудника

Предлагаю первым проверить Keycloak 26.8.2. Он документирует нужные для сценария вход, проверку email и смену адреса без собственного потока проверки. authentik 2026.8.5 подходит при дополнительной настройке проверки email. ZITADEL 4.20.2 тоже покрывает протокол, но его стандартная установка включает отдельный Login UI. Это рекомендация для проверки, продукт ещё не выбран.

Исследование отвечает на вопрос [«Исследовать варианты корпоративного OIDC для принятого сценария»](https://github.com/KirillSachkov/ai-first-platform/issues/54) для [карты подготовки решения](https://github.com/KirillSachkov/ai-first-platform/issues/51). Источник требований, включая P01–P08, это [принятая спецификация подключения сотрудника и агента](https://github.com/KirillSachkov/ai-first-platform/issues/48). Более ранние открытые вопросы в документах `main` её не отменяют.

## Личность и адресат приглашения

OIDC определяет стабильную личность парой `iss` и `sub`. Email может измениться и позднее перейти другому человеку. `email_verified=true` означает, что провайдер проверил контроль адреса в момент проверки. Это не доказывает трудовые отношения или разрешения платформы. Scope `email` запрашивает адрес и статус проверки, но приложение должно проверить фактическое наличие и значение claims. Основание: [OIDC Core, разделы 2, 5.1, 5.4 и 5.7](https://openid.net/specs/openid-connect-core-1_0.html).

Следствие для проектирования: при принятии приглашения платформа сопоставляет его адресата с подтверждённым email доверенного провайдера. После принятия связь с сотрудником хранится через `iss` и `sub`. Один `login_hint`, совпадение домена или владение ссылкой не подтверждают адресата. При обычном повторном входе email не должен заново связывать личность с другой учётной записью. Это вывод из OIDC и принятой персональности приглашения, а не готовый контракт приложения.

| Кандидат | Стабильная личность | Подтверждение и изменение email |
| --- | --- | --- |
| Keycloak | ID Token получает `sub` из ID пользователя. Настройки дополнительных мапперов могут изменить результат; конфигурацию нужно закрепить. | Есть `VERIFY_EMAIL` с письмом. При включённой проверке `UPDATE_EMAIL` сохраняет новый адрес как ожидающий подтверждения. |
| authentik | Есть режимы `sub` по внутреннему ID/UUID, а также по email или username. Для нашего сценария предлагается UUID; изменяемые адрес и имя непригодны. | С 2025.10 стандартный scope возвращает `email_verified=false`. Нужны email stage, политика записи проверенного адреса и свой scope mapping. |
| ZITADEL | Документация выдаёт `sub` как Subject ID пользователя. | Есть `email` и Boolean `email_verified`. Их присутствие в ID Token зависит от настроек; нельзя предполагать, что они всегда там есть. |

Источники таблицы: [Keycloak TokenManager 26.8.2](https://github.com/keycloak/keycloak/blob/e514445f9dcdabc5bdcf67cab56c1e49655de067/services/src/main/java/org/keycloak/protocol/oidc/TokenManager.java#L1437), [Keycloak Server Administration 26.8.2](https://www.keycloak.org/docs/26.8.2/server_admin/), [authentik ID Token 2026.8.5](https://github.com/goauthentik/authentik/blob/4ec0d19b98da3c329781894cd550da95d3033954/authentik/providers/oauth2/id_token.py#L139), [стандартный email mapping authentik](https://github.com/goauthentik/authentik/blob/4ec0d19b98da3c329781894cd550da95d3033954/blueprints/system/providers-oauth2.yaml#L27), [claims ZITADEL](https://zitadel.com/docs/apis/openidoauth/claims).

У authentik официальная [инструкция проверки адреса](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/verify-email-address/) отдельно предупреждает о смене email через администратора, другие потоки и синхронизацию источника. Возврат `false` сам по себе не запрещает вход. Постоянное `email_verified=true` без проверенного процесса не подходит. Инструкция прочитана в текущей документации; её полный поток на релизе 2026.8.5 здесь не запускался.

У ZITADEL [API смены email](https://zitadel.com/docs/reference/api/user/zitadel.user.v2.UserService.SetEmail) позволяет указать статус проверки или получить/отправить код. Сам endpoint уже отмечен устаревшим в пользу `UpdateUser`. Поэтому конкретный поддерживаемый путь смены адреса и повторной проверки надо закрепить в конфигурации и проверить на выбранной версии. Наличие административного флага не доказывает прохождение проверки ящика.

## Первый администратор и повторные входы

Оператор создаёт или подключает корпоративную личность в IdP. Отдельно платформа выдаёт первое административное приглашение явно заданному адресату. Учётная запись сотрудника появляется только после принятия. Администратор IdP не получает автоматически полномочия платформы. Это разделение следует из P01 и правила создания сотрудника в спецификации.

У Keycloak [bootstrap admin](https://www.keycloak.org/server/bootstrap-admin-recovery) создаёт временный административный доступ к самому Keycloak. Он не заменяет первое приглашение платформы. Предлагаемая настройка для проверки использует отдельный realm сотрудников и обычную личность получателя; bootstrap-доступ нужен оператору провайдера.

| Ситуация | Что уже задано спецификацией или следует проверить |
| --- | --- |
| Личность уже есть в IdP, сотрудника ещё нет | Вход подтверждает личность; сотрудник появляется при принятии действующего приглашения. |
| Та же личность входит повторно | Остаётся одна учётная запись. Гонки и повтор callback не должны создавать дубликаты. |
| Сотрудник деактивирован платформой, IdP продолжает пускать | Новые выдачи запрещены. Успешный OIDC-вход и старое приглашение не восстанавливают доступ. |
| Активному сотруднику выдали ещё одно приглашение | Новая учётная запись недопустима; точный ответ интерфейса и судьба приглашения ещё требуют решения. |
| Email изменился у прежнего `iss` + `sub` | Личность остаётся прежней. Приглашение на прежний адрес не совпадает с новым email. Обновление контактных данных и порядок перевыдачи ещё предстоит определить. |
| Пользователь IdP удалён и создан заново с тем же email | Новую пару нельзя автоматически присоединять к старой учётной записи по email. Процедура восстановления связи ещё не определена. |

Отказ автоматически связать новую пару со старой учётной записью предложен на основании OIDC, это ещё не принятое новое требование. Защита последнего администратора и восстановление участий остаются правилами платформы, их не решает выбор IdP.

## Браузерный вход и локальное окружение

Все три продукта документируют Authorization Code Flow с PKCE, то есть обмен кода с доказательством владения исходным случайным секретом. Для проверки предлагается `S256`, точные callback URI, `state` и `nonce`. У Keycloak PKCE можно сделать обязательным настройкой клиента; пустое значение не требует его от каждого запроса. Источники: [настройки Keycloak 26.8.2](https://www.keycloak.org/docs/26.8.2/server_admin/), [OAuth2 authentik](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/), [Code Flow и PKCE ZITADEL](https://zitadel.com/docs/guides/integrate/login/oidc/login-users).

React SPA не может хранить client secret. Если обмен выполняет браузер, нужен public client; если backend, secret может храниться на сервере. Это ограничение подтверждает [Keycloak JavaScript adapter](https://www.keycloak.org/securing-apps/javascript-adapter). Расположение обмена и хранение сессии ещё не выбраны. Корпоративный OIDC-вход также не доказывает поддержку авторизации MCP выбранным клиентом.

| Кандидат | Документированная локальная установка и ограничения |
| --- | --- |
| Keycloak | Есть один контейнер `start-dev` и импорт realm. Нужно задать лимит памяти; пример использует 1 GB, рекомендация 2 GB относится к малой production-установке. Это не измерение полного стенда. |
| authentik | Compose требует минимум 2 CPU и 2 GB RAM. В закреплённом Compose есть PostgreSQL 16, server и worker; Redis в этом файле нет. |
| ZITADEL | Текущий quickstart требует Docker Engine 24+, Compose и минимум 2 GB RAM. Базовый стек включает proxy, API, Login UI и PostgreSQL. |

Источники: [контейнер Keycloak](https://www.keycloak.org/server/containers), [установка authentik](https://docs.goauthentik.io/install-config/install/docker-compose/), [Compose authentik 2026.8.5](https://github.com/goauthentik/authentik/blob/4ec0d19b98da3c329781894cd550da95d3033954/lifecycle/container/compose.yml), [Compose ZITADEL](https://zitadel.com/docs/self-hosting/deploy/compose). В [`.env.example` ZITADEL на ревизии 4.20.2](https://github.com/zitadel/zitadel/blob/dce17d591309b1c0cdfb6c6718ec6cfada05eb7d/deploy/compose/.env.example#L34) стоит `v4.16.0`. Копирование quickstart не гарантирует испытание релиза 4.20.2; версии образов надо закрепить отдельно.

Отправка приглашений платформой не входит в спецификацию. Однако письмо для подтверждения адреса у IdP требует настроенной доставки. Для локальной проверки можно предложить изолированный SMTP-приёмник. Это план, он здесь не установлен. Issuer, discovery и JWKS должны быть доступны и браузеру, и backend; адрес контейнера, недоступный браузеру, не заменяет согласованный issuer.

## План проверки и пределы результата

Сервисов, credentials, кода приложения и тестов это исследование не меняло. Контейнеры и браузерный вход не запускались. Не измерялись память, время старта, доставляемость писем или совместимость с NestJS и MCP. Лицензии приведены по файлам продуктов; юридическая оценка не проводилась.

У отчёта проверены 26 уникальных ссылок, все вернули HTTP 200. Проверки пробелов и отсутствия длинного тире прошли. `pnpm check` не прошёл: в окружении Node 25.2.1 при требовании `>=26`, а `prettier` отсутствует. Зависимости для исследования не устанавливались.

После отдельного разрешения на эксперимент оператор тестовой среды сможет выполнить следующий план с Keycloak 26.8.2:

1. Закрепить образы, issuer, отдельные порты, realm и конфигурацию OIDC-клиента. Согласовать владельца сервисов по правилам общих ресурсов проекта. Сохранить конфигурацию без секретов.
2. Подготовить адресата A, другого сотрудника B и личность с неподтверждённым адресом. Проверить реальное письмо, переход по ссылке и изменение claims, не заменяя это ручным выставлением флага.
3. Пройти Code Flow с `S256`. Сохранить обезличенные claims `iss`, `sub`, `email`, `email_verified`, `aud` и результаты отрицательных проверок callback, `state`, `nonce` и неверного verifier.
4. Войти повторно и подтвердить прежний `sub`. Поменять email штатным способом, затем через администратора; зафиксировать pending-состояние, повторную проверку и неизменность личности. Удаление и повторное создание проверить только на одноразовой тестовой личности.
5. Когда появится реализация приглашений, выполнить P01–P03 и P-H01: B не принимает ссылку A, неподтверждённый адрес не создаёт сотрудника, повтор не создаёт дубликат. Проверить заменённую ссылку и уже существующего сотрудника согласно согласованному ответу интерфейса.
6. Выполнить P07–P08: деактивировать сотрудника в платформе при живой IdP-сессии, проверить отказ нового запроса, затем явное восстановление без возврата прежних назначений. Владелец или назначенный администратор принимает P-H01 по записи сценария и результатам E2E с настоящим IdP.

**Что предстоит решить владельцу при подготовке решения**

- Подтвердить кандидата для эксперимента. Рекомендация: Keycloak 26.8.2; два других продукта остаются запасными вариантами.
- Определить, кто и каким процессом подтверждает корпоративные адреса, включая административную смену. Утверждение IdP должно относиться к текущему адресу.
- Уточнить сравнение адресов, повторное приглашение действующего сотрудника, смену email и потерю прежнего `sub`. Без решения нельзя обещать автоматическое связывание или восстановление.
- Выбрать способ браузерной сессии и согласовать отдельный эксперимент с окружением. Приёмка P-H01 сохраняется; документальное исследование её не заменяет.
