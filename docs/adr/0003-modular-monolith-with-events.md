# Модульный монолит со схемой на модуль и событиями между модулями

Принято с владельцем 30 октября 2026 года в задаче [«Каркас платформы: стек, модули, Docker Compose и проверки готовности»](https://github.com/KirillSachkov/ai-first-platform/issues/13).

Backend — один процесс, разделённый на модули предметной модели. У каждого модуля своя схема PostgreSQL и свои миграции; модуль читает и пишет только свои таблицы, а на чужие сущности ссылается идентификаторами. Чтение и проверки между модулями — синхронные вызовы публичных контрактов. Изменения бизнес-данных между модулями — асинхронные интеграционные события через outbox в схеме издателя, RabbitMQ и inbox в схеме подписчика, без транзакций между модулями. Так модуль можно позже вынести в отдельный сервис без смены способа взаимодействия.

## Рассмотренные варианты

- **Общая транзакция между модулями.** Проще в первых сценариях. Отклонена: связывает схемы модулей и не переживает вынос модуля в сервис.
- **Отдельные сервисы с самого начала.** Отклонены: эксплуатационная цена без пользы для первой версии.
- **Внутрипроцессная шина событий без брокера.** Отклонена: события теряются при сбое процесса, а повторная доставка и dead-letter очередь пришлось бы писать самим.

## Последствия

- Решение «выдавать сведения или нет» принимается синхронным чтением источника истины. События выполняют последствия, например прекращение участий и отзыв подключений, и могут прийти с задержкой.
- Обработчики идемпотентны (inbox) и учитывают момент события, чтобы запоздавшее событие не отменило более позднее изменение.
- Тесно связанные модули, которым нужна общая транзакция, лучше объединить, чем связывать транзакцией.
- Механизм outbox и inbox появляется вместе с первой фичей, которая публикует событие.
