# Первая версия платформы

Согласовано с владельцем 29 октября 2026 года в задаче [«Выбрать первый законченный сценарий и границы первой версии»](https://github.com/KirillSachkov/ai-first-platform/issues/2).

## Назначение

Платформа — внутренний инструмент компании для организации AI-first разработки вокруг готовых агентов. Начальная аудитория — разработчики. Сотрудник сам запускает своего агента на своей машине и подключает его к платформе.

Общая цель — удобная повседневная разработка на всём пути от проектирования задач людьми с помощью агентов до выполнения, проверок и вливания изменений по правилам конкретного репозитория. Полный цикл — цель развития платформы, а не обязательство реализовать все его механизмы в первой версии.

Польза оценивается по удобству работы разработчика с платформой в целом. Отдельная демонстрационная задача не определяет состав продукта. Для первой версии проверяем перечисленные ниже возможности; улучшение скорости разработки пока не заявляется как доказанный результат.

## Основная поставка

- Учётные записи сотрудников, приглашение и вход в платформу.
- Создание проектов и управление участием сотрудников. Участие в компании само по себе не открывает все проекты.
- Проект объединяет один или несколько репозиториев, сотрудников, разрешения и инструкции для работы.
- Сотруднику и его агенту доступны только разрешённые проекты. Участие в проекте открывает сведения обо всех его репозиториях.
- Подключение одного выбранного готового агента разработчика. Конкретного клиента и способ подключения предстоит выбрать отдельно.
- Агент получает разрешённые проекты, репозитории и инструкции, по которым может подготовить окружение и проверить доступ к коду.
- При уходе сотрудника прекращается его доступ к платформе; подключённый агент перестаёт получать сведения компании через платформу. Детальные правила отзыва доступа уточняются отдельно.

Основная поставка использует репозитории, к которым у сотрудника уже есть действующий доступ. Разрешение видеть сведения о репозитории в платформе само по себе не выдаёт права в GitHub.

## Дополнительный этап: GitHub-доступы

Отдельный модуль интеграций связывает платформу с внешними сервисами. Первая интеграция — GitHub.

На дополнительном этапе сотрудник связывает GitHub-аккаунт с аккаунтом платформы. Платформа выдаёт и отзывает доступ к репозиториям разрешённых проектов; при уходе сотрудника отзывает выданный ею доступ. Этот этап расширяет основную поставку и не является условием первого подключения агента к заранее доступному репозиторию.

Управление GitHub-доступами и работа с GitHub Issues — разные возможности. Последняя не входит в этот этап автоматически.

## Граница ответственности

Платформа связывает сотрудников, проекты, репозитории, разрешения и инструкции и предоставляет разрешённые сведения сотруднику и его агенту.

Контекст агента, команды подготовки окружения, проверки и правила разработки могут находиться в репозиториях. Платформа не обязана переносить или дублировать их. Если проект объединяет несколько репозиториев, общий порядок работы также может быть описан в Git. Способ связи платформы с источниками инструкций предстоит уточнить отдельно.

Окружение готовит сотрудник со своим агентом по существующим инструкциям. Платформа в первой версии не создаёт окружения, не управляет ими и не предоставляет удалённое место выполнения агента.

Код, PR, review, проверки и merge остаются в GitHub и процессе репозитория. Задачи ведутся в существующем внешнем трекере, например GitHub Issues. Сотрудник и агент могут работать с ним существующими средствами без интеграции задач в платформу.

## Признаки готовности

1. Ответственный может создать проект с репозиториями и инструкциями, пригласить сотрудника и открыть ему нужный проект.
2. Сотрудник входит и получает разрешённые сведения проекта; сведения чужих проектов ему недоступны.
3. Подключённый агент получает сведения в пределах прав сотрудника и может использовать инструкции для подготовки окружения и проверки доступа к заранее доступному коду.
4. После прекращения доступа сотрудник и его агент больше не получают сведения через платформу.
5. На дополнительном GitHub-этапе проверяется выдача и отзыв управляемых платформой прав на реальные репозитории.

Это критерии будущей реализации, а не отчёт о выполненных проверках приложения.

## Направления развития

- Интеграция с существующим трекером и отображение задач в платформе. Собственный трекер сейчас не планируется.
- Разделение ответственности платформы, трекера и GitHub в полном цикле работы: какие состояния и результаты видят человек и агент, где они хранятся и кто ими управляет. Это отдельный будущий вопрос, а не выбранная схема синхронизации.
- Наблюдение за ходом выполнения, исполнителями, PR и результатами проверок.
- Общие skills, распространение конфигураций агентов и управление рабочими процессами сверх передачи разрешённых инструкций и подключения выбранного агента.
- Команды, подробные роли, другие интеграции, контроль расходов, агент компании, облачное выполнение, качество, релизы и эксплуатация — возможные направления из исходного брифа; их порядок не согласован.

Production-среда сейчас не предполагается. Deploy, управление разными средами, диагностика и расширенное сопровождение онбординга не входят в первую поставку.

## Изменения относительно исходного брифа

- Сохраняются сотрудники, приглашения, проекты, репозитории, инструкции, ограничение доступа и подключение своего агента.
- Выдача и отзыв GitHub-доступов выделены в дополнительный этап; основная поставка работает с заранее доступным кодом.
- Подготовка окружения остаётся работой сотрудника с агентом по инструкциям проекта, включая инструкции в Git.
- Повседневная разработка и полный цикл до merge задают общую цель; интеграция задач, наблюдение и управление процессами отложены.
